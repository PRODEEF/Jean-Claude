# 100 — API Hono (`apps/api`)

## Couches et sens des dépendances

```
feature/  →  domain/  →  core/
```

`feature/` peut dépendre de `domain/`. **L'inverse est interdit** — c'est ce qui
garde les modules `domain/` réutilisables.

| Couche | Contenu |
|---|---|
| `core/` | Infrastructure transverse : config, supabase, auth, llm, http |
| `domain/` | Une entité métier par module : folder, conversation, task, calendar, user |
| `feature/` | Cas d'usage composant plusieurs domaines : assistant, search, health |

## Anatomie d'un module `domain/`

Référence à copier : `apps/api/src/domain/folder/`.

```
<entité>/
  <entité>.routes.ts                HTTP — validation Zod, aucune logique
  <entité>.service.ts               Logique métier — testable sans base
  <entité>.repository.interface.ts  Contrat consommé par le service
  <entité>.repository.ts            Supabase — seul fichier avec du snake_case
  <entité>.service.spec.ts          Tests sur doubles
```

**Pas de fichier de câblage.** Le service est construit en tête du fichier de
routes — `const service = new FolderService(folderRepository)`. Un fichier de
plus n'ajouterait qu'une indirection à relire.

Détail pas à pas : skill [api-module](../skills/api-module/SKILL.md).

## Règles

**Le service reçoit l'interface, jamais l'implémentation.**

```ts
// ✅
constructor(private readonly folders: IFolderRepository) {}

// ❌ — rend le service intestable sans base
constructor(private readonly folders: FolderRepository) {}
```

**Aucune forme `*_id` ne franchit la frontière du Repository.** Le mapping
snake_case ↔ camelCase vit dans `toEntity()`. Services, routes et clients ne
manipulent que les types de `@jc/domain`.

**Les Repositories utilisent `forUser(accessToken)`** de `core/supabase`. Les
RLS s'appliquent alors. `admin` contourne les RLS : réservé aux traitements
système (rappels planifiés), jamais dans un chemin déclenché par une requête
HTTP.

**Validation par route avec `validate()`** de `core/http.ts`, à partir des
schémas de `@jc/domain`. Elle rend un 400 dont le corps porte les erreurs par
champ — la forme que `@jc/api-client` sait déjà lire. Pas de `class-validator` :
il imposerait une seconde définition des mêmes règles, que l'app Expo ne
pourrait pas partager.

**Deux façons d'échouer, et une seule est visible du client.**

```ts
// ✅ message destiné à l'utilisateur
if (!folder) throw httpError(404, "Dossier introuvable.");

// ✅ panne technique — consignée, puis rendue en 500 générique
if (error) throw new Error(error.message);
```

Ne jamais faire remonter au client le message brut d'un fournisseur externe :
il peut contenir une requête SQL ou un fragment de prompt, donc des données
utilisateur.

**Un `undefined` laisse la colonne intacte, un `null` explicite l'efface.**
Construire les payloads d'`update` clé par clé :

```ts
const payload: Record<string, unknown> = {};
if (patch.name !== undefined) payload["name"] = patch.name;
if (patch.color !== undefined) payload["color"] = patch.color;
```

**Une conversation n'a pas de dossier parent unique.** Toujours passer par
`conversation_folders`. Ne jamais ajouter de colonne `folder_id` sur
`conversations` (§5.2, A.1).

**Aucun SDK de modèle IA hors de `core/llm/providers/`.** Importer `llm` et
parler à l'interface `LlmProvider`.
Voir skill [llm-provider](../skills/llm-provider/SKILL.md).

## Routes

- Préfixe `/api`, posé dans `app.ts` au montage de chaque groupe
- Routes littérales **avant** les routes paramétrées : `.get("/assistant")` doit
  précéder `.get("/:id")`
- `.use(auth)` en tête de tout groupe non public ; l'utilisateur se lit ensuite
  avec `c.get("user")`
- Tout `:id` passe par `validate("param", z.object({ id: uuidSchema }))` —
  sinon un identifiant malformé part jusqu'à Postgres et ressort en 500
- Pagination par curseur (`cursorPaginationSchema`), pas par offset
- Statuts : `201` à la création, `204` sur suppression

## Tests

Tout service touché doit avoir un `.spec.ts`. Doubles via l'interface du
Repository, jamais de vraie base. Voir rule [300-tests](300-tests.md).
