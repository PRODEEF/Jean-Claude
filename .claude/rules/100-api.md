# 100 — API NestJS (`apps/api`)

## Couches et sens des dépendances

```
feature/  →  domain/  →  core/
```

`feature/` peut dépendre de `domain/`. **L'inverse est interdit** — c'est ce qui
garde les modules `domain/` réutilisables.

| Couche | Contenu |
|---|---|
| `core/` | Infrastructure transverse : config, supabase, auth, llm, filters, validation |
| `domain/` | Une entité métier par module : folder, conversation, task, calendar, user |
| `feature/` | Cas d'usage composant plusieurs domaines : assistant, search, health |

## Anatomie d'un module `domain/`

Référence à copier : `apps/api/src/domain/folder/`.

```
<entité>/
  <entité>.controller.ts            HTTP — validation Zod, aucune logique
  <entité>.service.ts               Logique métier — testable sans base
  <entité>.repository.interface.ts  Contrat + symbole d'injection
  <entité>.repository.ts            Supabase — seul fichier avec du snake_case
  <entité>.module.ts                Câblage
  <entité>.service.spec.ts          Tests sur doubles
```

Détail pas à pas : skill [api-module](../skills/api-module/SKILL.md).

## Règles

**Le service dépend du symbole, jamais de la classe.**

```ts
// ✅
constructor(@Inject(FOLDER_REPOSITORY) private readonly folders: IFolderRepository) {}

// ❌ — rend le service intestable sans base
constructor(private readonly folders: FolderRepository) {}
```

**Aucune forme `*_id` ne franchit la frontière du Repository.** Le mapping
snake_case ↔ camelCase vit dans `toEntity()`. Services, controllers et clients
ne manipulent que les types de `@jc/domain`.

**Les Repositories utilisent `supabase.forUser(accessToken)`.** Les RLS
s'appliquent alors. `supabase.admin` contourne les RLS : réservé aux traitements
système (rappels planifiés), jamais dans un chemin déclenché par une requête HTTP.

**Validation par route avec `ZodValidationPipe`**, à partir des schémas de
`@jc/domain`. Il n'y a **pas** de `ValidationPipe` global — un pipe global
imposerait `class-validator`, donc une seconde définition des mêmes règles.

**Un `undefined` laisse la colonne intacte, un `null` explicite l'efface.**
Construire les payloads d'`update` clé par clé :

```ts
const payload: Record<string, unknown> = {};
if (patch.name !== undefined) payload["name"] = patch.name;
if (patch.color !== undefined) payload["color"] = patch.color;
```

**Une conversation n'a pas de dossier parent unique.** Toujours passer par
`conversation_folders`. Ne jamais ajouter de colonne `folder_id` sur
`conversations` (§5.2, A.1).

**Aucun SDK de modèle IA hors de `core/llm/providers/`.** Injecter
`LLM_PROVIDER` et parler à l'interface `LlmProvider`.
Voir skill [llm-provider](../skills/llm-provider/SKILL.md).

## Routes

- Préfixe global `/api`, posé dans `create-nest-app.ts`
- Routes littérales **avant** les routes paramétrées : `@Get("assistant")` doit
  précéder `@Get(":id")`, sinon `assistant` est capté comme un identifiant
- `@UseGuards(JwtGuard)` + `@ApiBearerAuth()` sur tout controller non public
- `@ApiOperation({ summary })` sur chaque route — c'est la doc de `/api/docs`
- Pagination par curseur (`cursorPaginationSchema`), pas par offset

## Tests

Tout service touché doit avoir un `.spec.ts`. Doubles via l'interface du
Repository, jamais de vraie base. Voir rule [300-tests](300-tests.md).
